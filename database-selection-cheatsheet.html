Database Selection Cheat Sheet

Start with the workload, consistency boundary, and access pattern. The product name comes last.

July 2026 Database architecture Quick reference 8 min read

Default to the simplest system that preserves the invariant

For a production application, that usually means relational first. Move to another model only when a measured requirement such as write scale, relationship traversal, text relevance, analytical scan volume, or latency makes the relational path a poor fit.

The diagram is a taxonomy, not a benchmark. Products can span multiple categories, and a production architecture often combines a primary store with a cache, search index, warehouse, or object-storage layer.

01

OLTP / operational

Production apps: relational is the default

Most application data has identities, constraints, updates, and relationships. SQL earns the first attempt.

Relational core

PostgreSQL
MySQL
SQL Server

Choose this for orders, payments, accounts, inventory, workflows, and other records where correctness spans multiple rows or entities.

Top interview pick: PostgreSQL gives you the broadest defensible default without inventing a special requirement.

Managed relational

Aurora
Cloud SQL
Azure SQL

Choose a managed service when the team values automated backups, patching, failover, monitoring, and cloud integration more than direct infrastructure control.

Call out: managed does not remove schema design, indexing, capacity planning, or recovery testing.

Specialized sidecar

MongoDB
Redis
Cassandra

Add a specialized store for one access pattern: documents, cache and ephemeral state, or partitioned high-volume writes.

Call out: polyglot persistence adds replication, consistency, backup, ownership, and incident complexity.

The strong interview move

Say: “I will start with PostgreSQL for transactional correctness. I would add or switch stores only after we quantify the access pattern or scale constraint it cannot meet.”

02

Use-case based

NoSQL: choose the data model from the query

“NoSQL” is not one design. The partition key, traversal, document boundary, or search index is the design.

Document

MongoDB
Couchbase
DocumentDB

Best when the application reads and writes self-contained aggregates with an evolving JSON-like shape.

Avoid forcing highly connected, frequently joined entities into duplicated documents.

Key-value

Redis
DynamoDB
Aerospike

Best when the key is known and access must be predictable: sessions, carts, counters, idempotency records, and hot lookups.

The key design is the schema. A bad partition key becomes the bottleneck.

Wide-column

Cassandra
ScyllaDB
HBase

Best for high write volume, large distributed datasets, and query-first denormalized tables.

Model from the read path. Do not promise ad hoc querying that the table layout does not support.

Graph

Neo4j
ArangoDB
Neptune

Best when variable-depth relationship traversal is the product: fraud rings, identity links, network paths, or knowledge graphs.

Use SQL when traversals are shallow and the team benefits more from relational simplicity.

Search

Elasticsearch
OpenSearch
Meilisearch

Best for full-text relevance, faceting, filtering, logs, and search-oriented retrieval.

Treat the index as a derived view. Keep an authoritative source and a reindexing path.

03

OLAP / warehouses

Analytics: separate storage, format, and compute

The diagram groups the ecosystem visually. In an interview, name the role each component plays.

Cloud warehouse

Snowflake
BigQuery
Redshift
Synapse

Optimized for large scans, aggregations, BI concurrency, and analytical workload isolation.

Pick from existing cloud, governance, skills, workload shape, and pricing model rather than logo popularity.

Lakehouse stack

S3
Delta Lake
Apache Iceberg

Object storage holds files. Delta Lake and Iceberg add table metadata and transaction semantics over those files. Engines such as Spark or Databricks process them.

This separation is the key interview distinction: storage is not the table format, and the format is not the compute engine.

Processing surface

Databricks Notebooks
Jupyter
Apache Spark

Notebooks are development interfaces; Spark is a distributed processing engine. Neither replaces the need for durable storage and governed tables.

Explain the path from ingestion to storage to transformation to serving.

Time series

InfluxDB
TimescaleDB
Prometheus

Choose based on whether you are storing product events, SQL-friendly time series, or operational metrics and alerting data.

Prometheus is a monitoring system with time-series storage, not a general-purpose application database.

04

Hybrid and emerging

Use a specialist only when the requirement is real

These systems can be excellent. They also create a new operational boundary, so the burden of proof is higher.

Distributed SQL

CockroachDB
TiDB
YugabyteDB

Useful when SQL semantics must span regions or scale horizontally.

Be ready to discuss latency, consistency, failure domains, and operational cost.

Multi-model

ArangoDB
OrientDB
Fauna

Useful when one operational system must support several data models with shared governance.

Convenience is not free; verify query quality, ecosystem depth, and lock-in.

Embedded / edge

SQLite
DuckDB
Realm

SQLite is a strong local transactional store. DuckDB is excellent for embedded analytical queries. Edge-first choices reduce network dependence.

Explain synchronization and conflict handling when data later moves to a central system.

Vector databases

Pinecone
Weaviate
Milvus

Useful for large-scale similarity search, metadata filtering, and retrieval workloads that exceed an existing relational extension.

Discuss recall, latency, filtering, index freshness, deletion, tenancy, and evaluation.

Real-time analytics

ClickHouse
Druid
Materialize

Useful for fast aggregations over fresh events, operational dashboards, and continuously maintained analytical views.

First ask whether a normal warehouse plus acceptable refresh latency is simpler.

Interview preparation

Ask these before naming a database

01 · INVARIANT

What must never be wrong? Balance, uniqueness, ordering, inventory, or ownership?

02 · ACCESS

What are the dominant reads and writes? Which keys, joins, traversals, or scans?

03 · SCALE

Data size, write rate, read rate, growth, skew, and geographic distribution?

04 · CONSISTENCY

Where is strong consistency required, and where is eventual consistency acceptable?

05 · OPERATIONS

Who owns backups, upgrades, failover, reindexing, migrations, and incidents?

06 · EVOLUTION

How will the schema, query mix, retention, and compliance requirements change?

A concise answer template

“Given this access pattern and this consistency requirement, I would start with this database because of these two properties. The main trade-off is this limitation. If this measured threshold appears, I would add or migrate to this specialist.”
